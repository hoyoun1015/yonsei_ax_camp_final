# 모델 선정 실측 (2026-08-11)

3-에이전트 full-loop 를 **동일 조건**(대표 과제 3개 · condition V · 프롬프트 v1)으로
세 모델에 돌려 비교했다. 재현: `python3 src/vccl/agents/pilot.py --model <모델>`

---

## 1. 그 전에 — `empty SUCCESS` 실패 모드를 잡았다

**증상.** `agy` 가 `status=SUCCESS` 를 돌려주면서 `structured_output` 과 `response` 가
모두 비어 있다. 사고 토큰만 소비하고 최종 출력이 없다. 첫 파일럿에서 **37호출 중 13회(35%)**
가 이렇게 실패했다.

### 원인은 `--json-schema` 강제 경로였다

변형별 12회 반복 (`src/vccl/agents/diagnose_empty.py`):

| 변형 | 성공 | 빈 응답 | 평균 토큰 | 평균 초 |
|---|---:|---:|---:|---:|
| A `--json-schema` (작은 스키마) | 12/12 | 0 | 24,408 | 16.2 |
| C `--json-schema` (확장 스키마) | **8/12** | **4** | 23,566 | 17.8 |
| **E 플래그 없이 프롬프트 지시** | **12/12** | 0 | **18,296** | **12.3** |
| F 확장 + 프롬프트 지시 | 12/12 | 0 | 19,068 | 15.3 |

**플래그 없는 경로가 24/24 로 안정적이고 25% 싸고 24% 빠르다.**
빈 응답은 플래그 경로에서만 나왔다.

### 함께 잡은 것 셋

**① `--effort` 는 쓸 수 없다.** `-high`/`-low` 가 붙은 모델명과 충돌해
`invalid model selection ... conflicts with --effort=low` 하드 에러가 난다(0 토큰).

**② 동일 요청 재시도는 무의미했다.** 실패가 프롬프트·스키마 조합에 결정적이어서
3회 재시도가 모두 같은 방식으로 실패했다. **경로를 바꾸는 재시도 사다리**로 교체했다.

```
1  플래그 없이 프롬프트 지시        (가장 안정적이고 저렴)
2  --json-schema 강제              (다른 코드 경로)
3  2 + "이전 응답이 비었다" 재요청
```

**③ enum 을 JSON 배열로 렌더링하면 안 된다.** 초안이 `"level": ["L1","L3"]` 로 적었더니
**claude-sonnet-4-6 이 "값이 배열이다"로 읽고 `{"level": ["L1"]}` 을 돌려줘 3/3 실패**했다.
Gemini 는 "둘 중 하나"로 읽어 우연히 통과했다. `"L1" | "L3"` 로 바꾸고, 키 존재뿐 아니라
**타입과 enum 소속까지 검증**하게 했다 — 그러지 않으면 배열 값이 통과해 뒤에서
`unhashable type: 'list'` 로 터진다.

**수정 후 세 모델 모두 실패 0.**

## 2. 모델 비교 — 동일 조건, 대표 과제 3개

| 모델 | 호출 | 실패 | 완주 | 오라클 정답 | 상승(분기A) | 호출당 토큰 | 총 토큰 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `gemini-3.6-flash-high` | 14 | **0** | 3/3 | **3/3** | 1 | 23,189 | 324,652 |
| `gemini-3.1-pro-high` | 14 | **0** | 3/3 | **3/3** | 1 | **12,532** | **175,459** |
| `claude-sonnet-4-6` | 16 | **0** | 3/3 | **3/3** | 2 | 20,829 | 333,269 |

**판단 품질로는 세 모델이 구분되지 않는다.** 과제 3개로는 당연한 결과이며,
이 파일럿의 목적은 품질 비교가 아니라 안정성과 quota 실측이다.

세 모델 모두 **밴드 C 과제에서 분기 A(escalate)를 발동**해 L1 → L3 로 올렸고
최종 결론이 오라클과 일치했다. closed loop 이 의도대로 작동한다.

## 3. quota 실측 — 통제 측정 (2026-08-11 재측정)

### 🔴 먼저, 이전 권고를 철회한다

**초판에서 `gemini-3.1-pro-high` 를 주 실행 모델로 권고했다. 그 근거가 잘못됐다.**

초판 근거는 파일럿 전후의 `/usage` 차이였다 — Flash 3%/16호출, Pro 1%/16호출.
여기서 "Pro 가 3배 저렴하다"고 결론 냈다. **두 가지가 통제되지 않았다.**

1. **5시간 창은 회전하며 회복된다.** 전후 차이는 «소비 − 회복»이지 소비가 아니다.
   실제로 Claude 실행 중 Gemini 가 72% → 73% 로 오르는 것을 관측했는데도
   그것을 보정하지 않았다.
2. **백분율이 정수**라 16호출 규모에서 해상도가 1%p 뿐이다. 3% 대 1% 의 차이가
   측정 잡음과 구분되지 않는다.

**통제 측정(동일 호출 20회 + idle 대조군)에서 결과가 뒤집혔다.**

### 통제 측정 결과

`src/vccl/agents/quota_probe.py` — 같은 프롬프트·같은 스키마로 N회 반복해 루프
변동성을 제거하고, 호출 없이 같은 시간을 대기하는 **idle 대조군**으로 회복분을
따로 재서 보정한다.

| | `gemini-3.6-flash-high` | `gemini-3.1-pro-high` |
|---|---:|---:|
| 성공 | 20/20 | 20/20 |
| 호출당 시간 | **11.8초** | 16.8초 |
| 호출당 토큰 | 18,020 | **11,615** |
| 캐시 적중 | 0 | 6,894 |
| 5시간 관측 감소 | 3%p | 3%p |
| idle 회복 | 0%p | +1%p |
| **5시간 보정 소비** | **3%p** | **4%p** |
| **5시간 창 용량** | **≈ 666회** | ≈ 500회 |
| 주간 용량 | **측정 불가** (<1%p) | ≈ 2,000회 |

**Pro 가 호출당 quota 를 «더» 쓴다.** 토큰은 36% 적은데 소비는 33% 많다 —
**quota 는 단순 토큰 가중이 아니다.** 그리고 Pro 가 42% 느리다.

부수 관찰 — 동일 호출 반복에서 Flash 는 캐시 적중이 0 이고 Pro 는 6,894 다.
파일럿에서는 둘 다 63~67% 였다. 캐시 정책이 모델·문맥에 따라 다르게 작동하는
것으로 보이나 확인하지 못했다. **Pro 의 낮은 입력 토큰이 캐시 때문인지 시스템
프롬프트 크기 때문인지 갈라내지 못했다.**

## 4. 결론 — 본실험 모델 배치 (잠정)

### `gemini-3.6-flash-high` — **provisional primary model**

5시간 창 용량이 Pro 보다 33% 크고(666 대 500), 30% 빠르며, 신뢰도가 같다(20/20).
대표 과제 3개에서 판단 품질도 뒤지지 않았다.

> ⚠️ **«잠정»인 이유 — 주간 용량을 모른다.** N=20 에서 주간 감소가 1%p 해상도
> 아래였다. Pro 는 2,000회로 나왔으나 Flash 는 미측정이다. **주간이 실제 상한일
> 가능성이 있고, 그 값을 모르는 상태에서 본실험 규모를 확정할 수 없다.**
>
> 별도 측정을 위해 quota 를 더 쓰지 않는다. 대신 **이후 모든 실행의 실제 사용량과
> `/usage` 변화를 누적해 추정한다** — 파일럿과 측정기가 자동으로
> `experiments/quota_ledger.jsonl` 에 append 하고,
> `python3 src/vccl/agents/quota_ledger.py` 로 현재 추정을 본다.

### 누적 원장의 현재 지표 (구간 6개 소급 적재)

| 모델 | 5시간 용량 | 주간 |
|---|---:|---|
| `gemini-3.6-flash-high` | ≈ 566회 | **미측정** (아래 잠정 지표) |
| `gemini-3.1-pro-high` | ≈ 850회 | ≈ 1,700회 |
| `claude-sonnet-4-6` | ≈ 61회 | ≈ 169회 |

**Flash 주간 — 잠정적 용량 지표.** 누적 34호출에서 주간 «관측» 감소가 0%p 였고
해상도가 1%p 이다. **회복이 없었다고 가정하면** 호출당 소비 < 0.0294%p 이고
용량 > 3,400회가 된다.

> ⚠️ **이것은 엄밀한 하한이 아니다.** 관측 감소 = 소비 − 회복이므로, 그 34호출 구간에서
> 회복이 일어났다면 실제 소비는 1%p 를 넘을 수 있다(예: 소비 0.8%p − 회복 0.8%p = 0).
> 5시간 창에서는 idle 대조군으로 회복을 0 으로 확인했지만 **주간 창의 회복은 측정하지
> 않았다.** 따라서 이 수치는 **«회복이 없다는 가정하의 잠정 지표»**이며
> **Stage B 동결의 근거로 쓰지 않는다.**

참고로 이 지표가 맞다면 N=92 예산(약 1,012회)은 주간 안에 들어간다. 그러나 확인 전까지
그것을 전제로 규모를 확정하지 않는다.

> 📌 **모든 추정이 회복 미보정 하한이다.** 관측 감소는 «소비 − 회복»이므로 실제 소비는
> 그보다 크거나 같고, 따라서 용량 추정은 **과대평가 방향**이다. Stage B 에서 여유를 둔다.

### 나머지 배치

| 모델 | 역할 | 근거 |
|---|---|---|
| `gemini-3.6-flash-high` | **잠정 주 실행 · 개발·디버깅** | 창 용량 최대, 최속 |
| `gemini-3.1-pro-high` | 고품질 확인 실험 (부분집합) | 주간 2,000회 확인됨 |
| `claude-sonnet-4-6` | 독립 replication (30~40과제) | 주간 ≈ 200회 — 전량 불가 |

> ⚠️ **역할별로 모델을 섞지 않는다.** 한 condition 안에서는 세 역할이 같은 모델을 쓴다.
> 섞으면 결과의 원인을 모델 차이에 귀속할 수 없다.
