작업 보고서 — 계산 복구와 D1 완결

2026-08-09 · Virtual Computational Chemistry Lab · 마감 9/2까지 24일

한 줄 요약 — D1 킬게이트를 전부 통과했다. 연구는 성립한다.

새벽에 메모리 초과로 머신이 죽어 작업 맥락을 잃었으나 파일과 계산 결과는 모두 살아 있었다. 원인을 잡고 안전한 실행 방식으로 교체한 뒤, 8개 서브셋 331구조 전량의 DFT 단일점을 완료했다(누락 0). 가장 중요한 게이트 G3(밴드 C 화학종 25종 이상, 15종 미만이면 폐기)가 33종으로 통과했다.

다만 보고 과정에서 내가 두 가지를 잘못 짚었고 이를 정정했다(§4). 그리고 설계대로 밴드를 확정하려면 L2(def2-SVP) 측정이 아직 필요하다(§5).

1. 무슨 일이 있었나 — 크래시와 복구

2026-08-09 새벽 계산 도중 머신이 죽었다. 원인은 메모리였다.

무엇이얼마를 요구했나결과

부수적으로 조용한 버그를 발견했다. 구 러너는 완료 판정을 sp.out 파일의 존재 여부로 했다. 죽다 만 잡이 영구히 "완료"로 건너뛰어지며, 그대로 두면 MAE에 조용히 반영됐을 것이다. 실제로 ACONF 3개가 이 상태였다.

실측 피크 RSS 2.2~3.4 GB. 이후 8개 서브셋을 전부 돌리는 동안 머신은 한 번도 죽지 않았다. 디스크 부족으로 세 번 멈췄으나 매번 가드가 정상 작동한 것이고 데이터 손실은 없었다.

가는 길에 실측으로 잡은 함정 둘

  • scf_subtype disk_df는 없는 옵션이다. psi4 1.11에서 out-of-core DF는 scf_type의 값이다.
  • PSI_SCRATCH는 절대경로여야 한다. psi4는 잡 디렉터리를 cwd로 실행되므로 상대경로를 넘기면 sp.out조차 만들지 않고 즉사한다.

사다리가 8개 전부에서 성립한다(1.7~5.0배). 계산 수준을 올리면 방법오차가 줄어든다는 RQ3의 전제가 특정 서브셋의 우연이 아니다. 그리고 τ가 서브셋 간 63배(0.193~12.190) 벌어진다 — 단일 τ로는 어떤 밴드도 제대로 나눌 수 없다는 것이 수치로 확정됐다.

반응 유형별 (시스템이 실제로 쓰는 τ)

기획안 §3.2가 요구하는 형태다. 반응 유형은 결합 그래프 비교로 에이전트가 직접 판정할 수 있어, 서브셋 정체를 노출하지 않는다.

1,000배 이상 차이다. "계산을 더 할지 말지"가 공짜 결정이 아니게 되며, 기획안이 우려했던 "잡당 0.3초에서 5회 절약은 과학적 통화가 아니다"라는 문제가 해소된다.

3. 게이트 판정 — 전부 통과

화학종 기준. 반응 유형별 τ로 산출했다.

게이트기준실측
G3밴드 C 화학종 ≥ 25 (15 미만이면 폐기)33종통과
G4밴드 A+B ≥ 50종85종통과
G4밴드 D ≥ 10종17종통과
G2DFT가 τ를 줄이는가1.7~5.0×통과
G6ZPVE·ΔE 일치—통과

G3가 이 연구의 생사를 가르는 게이트였다. 밴드 C가 비면 에이전트가 규칙 기준선 R0를 이길 구조적 경로가 없어 설계가 성립하지 않는다. 통과했다.

참고 — 반응 수 기준: A 60 · B 99 · C 45 · D 20. 게이트는 서브셋별 τ로 매겨도 동일하게 통과한다(C 33 · A+B 85 · D 17). G3 통과라는 결론은 τ 범위 선택에 좌우되지 않는다.

4. 무엇이 잘못되었나

정정 1 — "L2가 사다리에서 탈락했다"는 내 보고는 틀렸다

저장소에 L2가 두 개 있었고 내가 혼동했다.

이름정의상태
L2 (기획안 §3.1)B3LYP-D3(BJ)/def2-SVP DFT 단일점미측정
"L2" (tau_probe.py)xTB --opt 국소최적화측정됨, 나쁨

내가 잰 것은 후자다. 그런데 xTB 최적화가 나쁘다는 것은 기획안 §3.1이 이미 같은 근거로 사다리에서 제외한 사실이라 새 발견이 아니었다. 따라서 "사다리는 2단으로 간다"는 결론은 무효이며, 기획안의 3단 구성은 그대로 유효하다.

영향이 크다 — 에스컬레이션 밴드가 τ₃ < |ΔE_ref| ≤ τ₂로 τ₂ = L2 기준이므로, L2 없이는 밴드 C를 설계대로 정의할 수 없다. 현재 밴드는 τ₂ 자리에 τ_L1을 대입한 잠정값이다.

정정 2 — τ를 서브셋별로 둔 것은 설계 위반이다

기획안 §3.2가 이를 명시적으로 금지하며, 근거가 타당하다. τ는 에이전트가 런타임에 조회하는 시스템 부품인데 G5(오염 방어)가 서브셋 정체를 숨기도록 요구하고, 데모 트랙에는 서브셋 개념 자체가 없다. 조회할 수 없는 τ는 부품이 될 수 없다.

설계대로 반응 유형 2종으로 다시 재자 내가 "가장 중요한 대목"이라고 강조했던 ACONF 결론이 뒤집혔다.

ACONF 밴드 분포ABCD
서브셋 τ = 0.193 (금지된 범위)15000
conformer 유형 τ = 1.213 (설계대로)1770

"ACONF는 밴드 D 공급원이 아니다"라던 서술은 금지된 τ 범위가 만든 인공물이었다. ACONF는 여전히 유효한 공급원이다.

기획안 자체의 오류 — CDIE20 화학종 수

기획안은 CDIE20을 3종으로 상정했으나 실제로는 16종이다. 36구조 20반응이 3종일 수 없다. 총 화학종은 92종이 아니라 106종이다.

화학종 정의 — 확정했다

화학종 := 반응 그래프의 연결성분. 한 반응에 함께 등장하는 구조를 같은 화학종으로 묶고 이행적으로 닫는다.

처음에는 이름 규칙(접두사·번호)으로 뽑았는데 틀렸다. CDIE20에 R21 → P20, R28 → P26처럼 번호를 넘나드는 반응이 있어, 번호로 묶으면 한 반응이 두 화학종으로 쪼개진다. 그러면 pseudo-replication을 막으려고 화학종 단위를 도입한 §4.2의 취지가 그대로 깨진다.

5. 무엇이 필요한가

최우선 — L2(def2-SVP) 실측

밴드 C를 설계대로 확정하는 데 필요한 유일한 미측정 항목이다. def2-TZVP보다 훨씬 싸므로 331구조 전량이 반나절 이내일 것으로 본다(TZVP가 총 ~11시간이었고 SVP는 그보다 몇 배 빠르다).

cd "(진짜_이게_최종)/calibration"
nohup env SAFE_MEM_GB=3 KILL_RSS_GB=5 PSI4_THREADS=8 \
  python3 safe_dft.py ../data/reference/gmtkn55 dft_work <서브셋> def2-SVP \
  > logs/<서브셋>_L2.log 2>&1 &

단, 반드시 한 번에 한 서브셋씩. 동시 실행이 크래시의 원인이었다.

그 다음 순서는 이렇다.

기획안에서 고쳐야 할 것

  • §4.2 화학종 정의 — "분자식 클러스터"를 "반응 그래프의 연결성분"으로 명시
  • §4.1 CDIE20 화학종 수 — 3종 → 16종, 총계 92종 → 106종
  • §3.2 τ 표 — 실측값 삽입 (conformer 1.213/0.405, 구조이성질체 9.036/3.407)
  • §3.1 사다리 표 — L1·L3 실측 비용 반영 (L2는 측정 후)
  • 밴드 공급원 배정 — L2 측정 후 실측 분포로 재배정
  • L2 제거는 하지 않는다 — §4 정정 1 참조

6. 사용자가 해야 할 것

① API 요청 한도(RPD) 확인 — 나는 할 수 없다

D1 문서에 계속 열려 있는 항목이다. 본실험의 호출 예산이 여기 걸려 있어 조건 수와 과제 수를 확정하려면 필요하다. Anthropic 콘솔에서 일일 요청 한도를 확인해 주면 된다.

② 화학종 ±1 차이 확인 (선택)

ISO34 29 vs 28, ISOL24 23 vs 24, Amino20x4 20 vs 19. 기획안을 쓸 때 어떤 기준으로 세었는지 알려주면 맞추겠다. G3 통과 결론에는 영향이 없다(33종 대 목표 25종).

③ 디스크 공간 — 언젠가는 정리 필요

228 GB 중 206 GB가 차 있다(95%). 계산이 세 번 멈춘 직접 원인이었다. 내가 /private/tmp의 고아 파일 46 GB를 회수했으나 근본 해결은 아니다. sudo 없이는 120 GB가 어디 있는지 확인되지 않는다. 현재 남은 계산에는 지장이 없다.

확인된 것: ~/Library 23 GB · /Applications 28 GB · 홈 전체 40 GB. Yonsei_AX_Camp 폴더 정리는 의미가 없다 — 현재 프로젝트를 뺀 나머지 전부가 45 MB다.

7. 구조 추천 — 무엇부터 만드는가

구현 설계 §8의 원칙을 그대로 따르기를 권한다.

"LLM을 부르는 코드는 가장 마지막에 만든다. 1~7번까지가 LLM 없이 완결된다."

이유가 중요하다. 1~7번이 끝나면 API가 하나도 없어도 "τ 실측치 + 밴드 구성 + 규칙 기준선 성능"이라는 산출물이 남는다. 마감이 24일 남은 단독 연구에서 이것이 최악의 경우의 안전망이다. 에이전트가 실패해도 논문은 성립한다.

권장 순서

#모듈완료 판정LLM
1~4실행층 + τ 실측완료 (calibration/)—
5tasks/pairs.py 밴드 층화G3·G4 판정 완료, L2 후 확정—

10arms.py F·A·V본실행있음

지금 calibration/에 있는 것을 어떻게 할 것인가

현재 calibration/의 스크립트들은 게이트를 넘기려고 빠르게 쓴 것이고, src/는 비어 있다. 이것을 그대로 본체로 승격하지 말 것을 권한다. 다만 버리지도 말아야 한다 — 재개 캐시와 실측 근거가 여기 있다.

  • safe_dft.py의 안전 장치는 그대로 가져간다 — 직렬 실행, 성공 마커 판정, RSS 감시, 디스크 가드. 이것들은 크래시로 값을 치르고 얻은 것이다.
  • band_analysis.py의 연결성분 화학종 정의를 tasks/로 옮긴다. 표집의 전제이므로 단위테스트를 붙일 것.
  • dft_work/의 에너지 캐시는 보존한다. 331구조 재계산은 11시간이다.

덜어낼 위험

  • 동시 실행 금지를 코드로 강제할 것. 이번 크래시의 직접 원인이고, 사람의 기억에 맡기면 반복된다. 락 파일 한 줄이면 된다.
  • 완료 판정은 언제나 도구의 성공 마커로. 파일 존재로 판정하면 조용히 누락된다.
  • τ와 라벨은 동결 후 불변. 동결 시점을 문서에 남기고, 결과를 본 뒤에는 어떤 이유로도 수정하지 않는다(CLAUDE.md 불변조건 7).
